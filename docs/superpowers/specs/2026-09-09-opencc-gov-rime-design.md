# OpenCCGovForRime 设计

状态：用户已批准开始实施；实施与验证进度见[实施计划](../plans/2026-09-09-opencc-gov-rime.md)。

## 1. 目标与来源

用 GitHub Actions 跟踪指定 gov OpenCC 转换数据和 Rime 原方案，生成独立的大陆规范繁体派生方案。

转换上游：
<https://github.com/TerryTian-tech/OpenCC-Traditional-Chinese-characters-according-to-Chinese-government-standards>

采用 `t2gov/` 的文本字表与配置自行编译，不依赖 `rime/` 预编译文件的同步进度。该项目不是政府官方 OpenCC 项目，其映射也不声称与《通用规范汉字表》完全一致。保留上游许可和归属。

## 2. 方案范围与命名

| 上游 | 首批 schema |
| --- | --- |
| `iDvel/rime-ice` | `rime_ice`、`double_pinyin`、`double_pinyin_abc`、`double_pinyin_flypy`、`double_pinyin_jiajia`、`double_pinyin_mspy`、`double_pinyin_sogou`、`double_pinyin_ziguang` |
| `rime/rime-luna-pinyin` | `luna_pinyin` |
| `rime/rime-cangjie` | `cangjie5` |
| `rime/rime-wubi` | `wubi86` |

首批共 11 个。雾凇后续新增双拼自动纳入，但必须通过适配验证；不自动扩展到 T9、英文、反查或其他方案的衍生版。

- 内部 ID：`<原 schema_id>_gov`。
- 显示名称：保留原 `schema/name`，直接追加“大陆”或“大陸”。
- 后缀依据显示名称的简繁，不依据词库或默认输出。简繁不明或混用时由方案配置明确指定，不猜测。
- 不删词、不缩写；`__` 只是此前交流中的名称占位，不写进名称。

## 3. 输出行为与适配结构

共用一套项目专用 OpenCC 文件；分别适配四个方案家族，生成继承原方案的轻量配置。不复制完整原方案，不做万能自动适配器。

| 家族 | 行为 |
| --- | --- |
| 雾凇及双拼 | 保留现有简繁切换；简体路径不变，繁体路径转换为大陆规范繁体。 |
| 朙月 | 派生方案将四态字形选项收敛为简体／大陆规范繁体，不保留香港、台湾模式。 |
| 仓颉 | 保留简繁切换，注意其 `simplification` 开关启用代表简体，与雾凇方向相反。 |
| 五笔86 | 新增简繁开关，默认保持原方案的简体输出模式。 |

总体上保持原方案的默认简繁模式；默认繁体的派生方案改为输出大陆规范繁体。所有方案都支持简体和大陆规范繁体，不强制只输出繁体。

本地雾凇案例的 `s2t` → `t2gov_keep_simp` 链路可作参考，但不能把它的开关名、候选标签和滤镜位置原样套用到所有家族。大陆转换后仍须完成候选去重。

只增添本项目专用命名的 OpenCC 文件，并同步改写内部引用；不覆盖用户的 `s2t.json` 等通用文件。不修改原方案，不读取或发布私人词库、历史记录。

## 4. 自动更新与发布

数据流：检查上游 → 固定本次使用的提交 → 编译转换数据及生成派生方案 → 验证 → 打包并发布 Release。

- 每三天检查一次，同时支持手动触发。
- 跟踪转换数据和原方案变化；有关变化触发重新生成。
- 验证通过即自动发布，无需人工审核。
- 获取、生成或验证失败时，不发布失败产物，保留上一版。
- 包内记录上游提交及实际验证版本，便于追溯。
- 不新增用户端版本检测、更新通知或主动更新提示。

调度实现须保持跨月的三天间隔语义，不能把按月重置的 cron 日字段 `*/3` 当作严格每三天。具体调度与状态保存方式在实施计划中确定，不要求 GitHub Actions 提供精确到时刻的运行保证。

## 5. 交付与平台

面向鼠须管（macOS）、小狼毫（Windows）、中州韵（Linux），共用产物。

产物只包含派生方案、所需 OpenCC 文件、安装说明、版本记录及许可文件。用户自行安装原方案，不打包原词库、Lua 或完整输入法环境。

文档说明各平台安装位置以及实际验证版本。平台支持目标不等于已有三端实测证据，也不承诺全部历史版本或任意用户自定义配置兼容。

## 6. 发布验证

在隔离测试环境中验证，不操作用户正在使用的 Rime 目录：

1. 对应原方案可以部署，确保测试基线有效。
2. 每个派生方案可以部署，依赖和 OpenCC 引用完整。
3. 简体模式的候选输出相对原方案保持不变。
4. 繁体模式的代表性字词符合指定上游的转换预期。
5. 开关可切换，默认简繁模式正确；朙月仅剩两种文字模式。
6. 转换后的相同候选不会重复。
7. 发布包不包含会覆盖通用 OpenCC 配置的同名文件，也不包含私人数据。

每种家族均需运行行为检查，不能只验证 YAML/JSON 能解析。具体测试工具、运行平台矩阵和字词样例在实施计划中选定；无法执行必要验证时阻止自动发布，不以未运行的检查冒充通过。

## 7. 实施边界

不创建万能适配框架，不捆绑完整输入方案，不生成简体与繁体两个独立派生版本，不新增通知系统。

用户已在设计讨论后授权自动本地提交和维护忽略规则，但未授权推送或创建远端仓库。Actions 自动发布 Release 是已经确认的目标行为，实际启用发生在用户发布仓库与工作流之后。

实施依据：[实施计划](../plans/2026-09-09-opencc-gov-rime.md)，具体化配置依赖、命名判定、滤镜适配、三天调度和可运行验证。
